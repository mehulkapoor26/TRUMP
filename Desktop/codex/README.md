# TRACEGUARD

TypeScript npm and Python repository dependency scanner with a React workspace, CycloneDX SBOMs, scoped JavaScript static analysis, downloadable security reports, and an npm VS Code extension.

Python scanning now supports requirements files, pyproject.toml and Poetry lock metadata using the existing workflow. See [Python support, live demonstration and limits](docs/PYTHON-SCANNING.md). Python source reachability is explicitly UNKNOWN; uploaded code is never installed or executed.

For the repeatable judge walkthrough, use [Judge demo and installation](docs/JUDGE-DEMO.md). See [verified results and remaining limits](docs/VERIFICATION.md) for the integration/security audit performed on 1 November 2026 (IST).

For a controlled npm project with **real published vulnerability data**, follow [the live repository-to-report demonstration](docs/PUBLISHED-DEMO.md): start `npm run dev`, then run `npm run demo:live` in another terminal. This is separate from the synthetic offline demo.

## Quick start

Requires Node.js 22.12+ and npm 10+.

```sh
npm ci
npm run dev
```

Open http://127.0.0.1:5173. The connection card calls `/api/health` through Vite's proxy to the Express server at http://127.0.0.1:3001. Use **Check again** to refresh the live status. Both servers stop with Ctrl+C.

## Health API

`GET /api/health` returns HTTP 200 with a `HealthResponse` defined in `shared/src/index.ts`:

```json
{
  "status": "ok",
  "service": "traceguard-api",
  "timestamp": "2026-01-01T00:00:00.000Z",
  "uptime": 42
}
```

The timestamp and uptime (seconds) are generated by the running backend. Health checks are not cached. Fixtures are test data; the UI uses the live endpoint.

```sh
curl http://127.0.0.1:3001/api/health
curl http://127.0.0.1:5173/api/health
```

## Configuration and deployment

Defaults require no environment files. To change the backend port, set `PORT` for the backend and `API_PROXY_TARGET` for Vite, for example:

```sh
PORT=4001 API_PROXY_TARGET=http://127.0.0.1:4001 npm run dev
```

Rollup is pinned to 4.66.0 via a root override because the registry's selected 4.67.3 tarball was unavailable during setup. Keep the pin and lockfile together when updating dependencies.

Vite uses port 5173 and fails if it is occupied. The development proxy keeps browser requests same-origin without requiring CORS. After `npm run build`, `npm start` serves both the frontend build and API at http://127.0.0.1:3001. A separate static host can also serve `frontend/dist` and reverse-proxy `/api` to the backend. Vite preview is a static preview without an API proxy. The backend binds to loopback; adjust the bind address intentionally if deploying in a container. Scan records and reports persist as local JSON files; authentication, multi-tenant authorization, automated retention and a tracing pipeline are not implemented.

Tailwind uses its official [Vite plugin](https://tailwindcss.com/docs/installation/using-vite); API forwarding uses [Vite server proxy configuration](https://vite.dev/config/server-options#server-proxy).

## Repository and ZIP scans

Use the **Scan an npm project** form to submit a public repository URL (`https://github.com/owner/repository`, optionally ending in `.git`) or one ZIP archive. GitHub scans retrieve the default branch anonymously. Private repositories, branch URLs, credentials, query strings, and redirects are rejected; GitHub rate limits can cause a retriable error.

- `POST /api/scans` with JSON `{ "url": "https://github.com/owner/repository" }`.
- `POST /api/scans` with multipart field `archive` containing a `.zip` file.
- `GET /api/scans/:id` retrieves the saved result; successful submissions return HTTP 201, a UUID, and a Location header.

For npm inputs, the scanner inventories `package.json`, `package-lock.json`, and `npm-shrinkwrap.json` at all depths, excluding installed and Git directories. Python inputs additionally detect requirements files, `pyproject.toml` and `poetry.lock`; Python-only and mixed repositories are supported. npm JSON files must contain an object, and npm-only scans require a manifest. Python dependency metadata is accepted without package.json. Results include file metadata, a resolved dependency graph, and a schema-validated CycloneDX 1.6 SBOM. Static dependency analysis is available immediately; optional OSV version-advisory checks are available from the graph. Application exploitability is not assessed. Yarn/pnpm lockfiles are outside the npm scan scope.

Default safety limits are 10 MiB compressed ZIP/download, 50 MiB expanded total, 10 MiB per entry, 2 MiB per metadata file, 5,000 entries, 200:1 compression ratio, and a 15-second inspection deadline. The compressed, expanded, file-count, and inspection-time limits can be configured with `TRACEGUARD_MAX_ZIP_BYTES`, `TRACEGUARD_MAX_EXPANDED_BYTES`, `TRACEGUARD_MAX_FILES`, and `TRACEGUARD_INSPECTION_TIMEOUT_MS` (bounded respectively at 100 MiB, 500 MiB, 50,000 files, and 120 seconds); `/api/scans/limits` reports active settings to the upload form. All files are streamed sequentially and checked for size and CRC integrity; paths with traversal, absolute paths, backslashes, control characters, colons, or case-insensitive duplicates are rejected. Symlinks, special files, encrypted entries, and unsupported compression are rejected. Nested archives are not unpacked. `node_modules`, `.git`, Python environments/caches, Gradle caches, and common generated output directories (`target`, `dist`, `build`, `coverage`) are excluded from project discovery. Archive paths are never extracted to disk. A bounded source snapshot is stored inside the private scan record for static analysis; no Git process is invoked and no package installation, lifecycle scripts, or submitted source code is executed. GitHub retrieval uses one fixed codeload HTTPS request for HEAD, without credentials, redirects or automatic retries, with a bounded body and a 30-second deadline. Archive-service rate limits stop retrieval and return HTTP 429 plus Retry-After. GitHub and ZIP inputs converge on the same archive inspection and analysis pipeline.

At most two submissions run concurrently per server, with ten submission attempts per IP per minute. The loopback development server does not trust forwarded IP headers. Configure a trusted reverse proxy deliberately before deployment.

Scan results (including dependency graphs, SBOMs, and bounded source snapshots) are retained in `.traceguard/scans` relative to the backend working directory (override with `SCAN_DATA_DIR`). Results survive restarts. Raw manifests are not retained; captured application source is retained in the private scan record. Normal scan responses return only source file metadata, while analysis responses intentionally include source snippets as evidence. Package names, requested dependency specifications, and installation paths appear in results and SBOMs. Delete stored JSON records when no longer needed. This local starter has no authentication or automatic retention policy; scan results are accessible to anyone with a scan ID who can reach the server. Persistent storage, access controls, and multi-instance rate/concurrency limits need deployment-specific configuration.


## Dependency graphs and CycloneDX SBOMs

New scans parse real manifests and npm lockfile versions **1, 2, and 3**, including npm-shrinkwrap.json (which takes precedence over a sibling package-lock.json). Each installation location has a stable component reference within its lockfile context. Different versions of the same package, and separate installations of the same version, retain separate identities. Equivalent npm package URLs (purls) can repeat for separate installed instances; their `bom-ref` values remain distinct.

`graph.nodes` records package names, locked versions, installation paths, and direct/transitive flags. `graph.edges` records parent and child IDs, the dependency's declared name, requested specification, and runtime/dev/optional/peer kind. A package may be both direct and transitive. Hoisted dependencies resolve by walking parent installation directories; peer dependencies resolve from the consumer's parent context. Workspace links resolve to canonical local package entries, with their manifests and dependencies read as data. Aliases use the actual package identity when supplied by the lockfile. Project roots and workspace projects are included as application components; lockfile dependency packages are library components.

Unresolved dependencies are listed in `graph.unresolved`; no registry request or package installation is performed to fill gaps. A manifest without a lockfile produces project metadata and unresolved declarations, not invented resolved versions. Stale ranges, missing versions, absent optional/peer packages, unsupported workspace link targets, and missing manifests produce warnings. Warnings or unresolved dependencies mark the SBOM composition incomplete. Unknown lockfile versions, malformed dependency maps, and unsafe lockfile paths fail the scan with HTTP 422. The graph is limited to 10,000 components and 50,000 relationships/unresolved declarations. Local links must point inside the lock's package map; external file targets are not fetched.

The result card shows package instances, resolved versions, dependency relationships, warnings, and a **Download CycloneDX JSON** link. Download with:

```sh
curl --fail http://127.0.0.1:5173/api/scans/SCAN_ID/sbom -o traceguard.cdx.json
```

`GET /api/scans/:id/sbom` returns `application/vnd.cyclonedx+json` with an attachment filename. Older stored scans without an SBOM return HTTP 409 and must be rescanned. Each new result persists its graph and SBOM together. The SBOM uses the scan UUID as its serial number and a synthetic metadata application component to contain all scanned project roots.

Every SBOM is validated before persistence and again before download against the vendored official [CycloneDX 1.6 JSON schema](https://cyclonedx.org/schema/bom-1.6.schema.json), with Ajv, standard/internationalized formats, and offline referenced schemas. Additional checks reject duplicate component references, dangling edges, duplicate dependency entries, and missing graph entries. No external schema is fetched at runtime. Component properties preserve lockfile context, install location, and direct/transitive flags; edge kinds and requested ranges are available in the scan graph. Static lockfile analysis cannot prove what is installed at runtime, recover undeclared dependencies, or select the host platform's optional package subset.

Tests include npm-generated v1/v2/v3 fixtures with three `is-number` versions, nested and hoisted relationships, duplicate same-version instances, scoped packages, aliases, workspaces, peer dependencies, cycles, incomplete data, malformed input, schema failures, attachment downloads, and the UI download link. Fixture provenance and regeneration are in `tests/fixtures/README.md`.


## Interactive dependency graph

After a scan, React Flow displays the actual parsed parent-to-dependency edges, with runtime/dev/optional/peer labels, zoom/pan controls, a minimap, and package-instance search. Duplicate versions and separate installation locations retain their original node IDs. Direct and transitive labels can both apply to one node. The canvas renders up to 300 nodes at once; its displayed node/edge counts make omissions explicit. Search all scanned instances and select one to prioritize it, representative root paths, and immediate neighbors on the canvas. The complete dependency graph and SBOM remain available even when the canvas is limited.

Click a node or choose a search result to see the version, installation path, lockfile context, immediate parents and children, requested dependency ranges, unresolved children, and one shortest path from each known project root. Path display is limited to five roots and 100 nodes per path, with omissions marked. Parent/child buttons navigate between package instances. Cycles terminate safely. Amber ancestors describe dependency impact through package relationships; these are not function call paths or proof that vulnerable code executes.

**Check vulnerability advisories** submits `POST /api/scans/:id/vulnerabilities`. The backend queries the fixed OSV HTTPS querybatch endpoint using npm package names and exact resolved versions; source files are never sent. Queries are deduplicated by name/version and matched results are mapped back to each corresponding installed instance. Project/workspace applications and packages without exact versions remain unknown. Advisory IDs link to OSV; red package nodes indicate version-advisory matches. Severity and exploitability scores are not invented.

The Findings page fetches up to 40 advisory ID/package detail pairs with a 15-second deadline and displays verified CVE aliases, source severity labels and CVSS vectors when supplied. Unavailable or unverified details remain explicit; severity is never guessed.

Results distinguish **advisory match**, **no known match**, and **unknown/not checked**. No known match is not a safety guarantee. Lookup time and coverage are displayed. Failed, malformed, paginated, or skipped responses remain unknown/incomplete rather than clean. Checks are limited to 1,000 unique pairs, batches of 100, 2 MiB responses, a shared 20-second deadline, two concurrent lookups per process, and six requests per IP per minute. Pagination is explicitly reported as incomplete. OSV reports are transient and refreshed on demand; they are not embedded in stored SBOMs.

**Dependency impact** counts ancestor instances in the lockfile graph. **Actual exploitability** is always explicitly marked **not assessed**: the optional scoped static call traversal below does not establish branch feasibility, runtime configuration, attacker-controlled input, deployment exposure, or mitigations. Advisory matching also does not independently verify package provenance. Development, optional, peer, and inactive platform dependencies can appear in the lockfile graph without running in a deployed application.

Run `npm test` for parser, model, OSV failure/coverage, API, and form checks. Run `npm run test:browser` for an actual ZIP upload, React Flow nodes/edges, node selection, paths, version-specific highlights, and exploitability wording in Chrome. On macOS the browser test uses installed Google Chrome; set `CHROME_EXECUTABLE` for another Chrome/Chromium path, or install Playwright Chromium on other platforms with `npx playwright install chromium`. The browser test starts development servers if needed. Its advisory response is mocked for deterministic highlights; production always uses the real OSV API.

References: [React Flow](https://reactflow.dev/learn/customization/custom-nodes), [OSV batch query API](https://google.github.io/osv.dev/post-v1-querybatch/).


## Scoped function reachability

Select a locked package instance in the graph, then open **Scoped function reachability** in its details. Choose a captured entry source file, an entry symbol (`<module>`, a named export, or `default`), and the affected package export. Package subpaths and an advisory ID can provide additional context. The API supports up to ten explicit entrypoints. Source paths are archive-relative, including any GitHub ZIP root prefix.

Function mapping is **user-declared, not independently verified**. OSV version-advisory matches do not automatically identify an affected npm function. Without an exported-function mapping, the result is UNKNOWN. An advisory ID is context only and is not treated as proof of that mapping. This implementation investigates calls to an exported API boundary, not reachability of an internal vulnerable implementation within a dependency.

`POST /api/scans/:id/reachability` accepts:

```json
{
  "entrypoints": [{ "file": "repo/src/server.js", "symbol": "handler" }],
  "target": {
    "packageNodeId": "COPY_THE_EXACT_NODE_ID_FROM_THE_SCAN_GRAPH",
    "exportName": "parse",
    "subpath": "",
    "advisoryId": "OPTIONAL_ADVISORY_ID"
  }
}
```

The selected locked package instance must have a resolved version. Imports are resolved through the nearest project/workspace's real dependency edges, so another installation/version of the same package cannot silently satisfy the target. Unresolved or transitive package boundaries without sufficient caller source stay UNKNOWN.

| Result | Meaning |
| --- | --- |
| `REACHABLE` | A syntactic call path from declared entries to the user-declared package export was found, with no detected gaps in the traversed closure. This is potential static reachability, not demonstrated runtime execution. |
| `NOT REACHABLE` | No matching call was found and the declared entry closure completed under the supported model. The UI always qualifies this as **within declared analysis coverage only**. |
| `UNKNOWN` | Missing mapping/source, unresolved entry/import, unsupported dispatch, ambiguous binding, parser failure, or a resource limit prevents a conclusive scoped result. Even a discovered candidate path remains UNKNOWN when detected gaps affect the analysis. |

Module initialization is always included for selected source files. Selecting a named/default exported function additionally includes that function as a root. Other exported functions are not assumed to be invoked by a framework or external caller. Local ESM module initializers are followed even when their imported functions are unused. The engine supports lexical direct function calls, function declarations, direct arrow/function-expression variables, direct IIFEs, local ESM imports/re-exports, named/default external function imports, and namespace calls such as `api.parse()`. It uses the TypeScript parser and symbol bindings in a virtual filesystem containing only captured source. It never reads a submitted tsconfig, loads plugins, installs dependencies, executes application code, or fetches missing modules.

Every response includes declared entrypoints, target mapping, boundary, captured/skipped source coverage, traversed files, visited function/call counts, completion status, source evidence (`file`, 1-based `line`/`column`, code snippet, edge kind, caller and callee), and analysis gaps. A positive report includes a representative call chain; negative reports include observed calls or entry evidence. At most 100 evidence records are returned, so a very long representative chain may be truncated. Reports are transient; the source snapshot persists with the scan.

Coverage excludes external library initializers and internals, uncaptured/generated code, node_modules, `.d.ts` declarations, CommonJS resolution, dynamic imports, computed calls, callbacks/escaping function references, aliases, object methods/getters, classes, JSX/framework dispatch, async/generators, native code, reflection, and mutation-dependent binding resolution. Encountered unsupported behavior in the traversed application closure creates a gap rather than a clean negative. Branches and loops are traversed syntactically without control-flow or path feasibility; even dead/conditional call sites may appear as potential static paths. Package exports/conditions, tsconfig path aliases, custom loaders, and bundler transformations are not modeled. Ambiguous extension resolution is UNKNOWN. Paths outside the explicitly selected entry closure are not evaluated, and a scoped negative must never be generalized to the entire application.

Source capture retains at most 200 `.js`, `.jsx`, `.ts`, `.tsx`, `.mjs`, or `.cjs` files, each at most 256 KiB, with 2 MiB total. Capture omissions are reported. Repositories previously scanned before this feature must be rescanned to capture source. Analysis runs in a separate fixed analyzer process with a six-second deadline and a 192 MiB V8 old-space limit (not a hard total-RSS limit). Traversal is limited to 1,000 units, 5,000 calls, and 100,000 AST visits; timeouts/crashes/limits return UNKNOWN. At most two analyses run simultaneously per server, with six attempts per IP per minute. Returned source snippets and the private on-disk source snapshot require the same access/retention controls as the repository; this local starter still has no authentication.

Dependency ancestry, advisory matching, and scoped function reachability are distinct evidence layers. None proves an exploitable application. Validate the advisory-to-function mapping and investigate runtime call feasibility, attacker control, deployment exposure, and mitigations separately.

The test suite covers reachable and unused handlers, named/default/namespace imports, lexical shadowing, duplicate package instances, package subpaths, recursion, incomplete source, invalid mappings, dynamic/indirect calls, callbacks, reassignment, syntax errors, the isolated analyzer process, private source storage, the HTTP route, and all three results with source evidence in Chrome. See the [TypeScript Compiler API documentation](https://github.com/microsoft/TypeScript/wiki/Using-the-Compiler-API) for the parser APIs.

Graph and reachability links accept `?node=ENCODED_NODE_ID` to open the exact package instance. The active scan selector, sidebar, and recent-scan links preserve scan context. Advisory checks are explicit, with package-name/version sharing disclosed beside the action. Charts are derived from actual graph edges and OSV report states. Unknown packages remain unknown; no synthetic severity, risk scores, activity history, or findings are displayed. ### Security reports

On a scan's **Overview**, select **Generate reports** under **Security reports**. Download **Security Findings** (what is wrong and why it matters) and **Remediation Plan** (fix and validation steps) separately as PDF or JSON. All four downloads use the same saved bundle ID, inventory hash, and evidence snapshot. Regeneration replaces that scan's previous snapshot; download it first if you need to retain history.

Generation performs fresh, bounded OSV version checks against the saved inventory, fetches advisory details, and checks candidate fixes against published npm metadata and fresh OSV results. A verified candidate means a published, non-deprecated advisory-listed release with no known OSV match at check time; compatibility is **not tested**. Failures, pagination, truncated evidence, missing fixes, and unknown coverage remain explicit. Reports do not prove runtime exploitability or guarantee safety. Recommendation references include advisory evidence and official npm guidance.

Server-recorded reachability is bounded to the latest result per package instance (100 instances per scan, 100 recent scans) in the current server process. It is not restored after restart; regenerate scoped analyses before producing a new report if needed. Saved reports survive restart alongside scan records. No submitted source or install scripts are executed during generation.

API: `POST /api/scans/:id/reports` generates and saves both reports; `GET /api/scans/:id/reports` reads the saved bundle; `GET /api/scans/:id/reports/{security-findings|remediation-plan}/{pdf|json}` downloads a report without rerunning external checks. Generation is rate limited and permits one concurrent job per server.

### Suspicious packages and supply chain evidence

Generate or regenerate security reports to see **Package supply chain signals** on Overview. Search or filter package instances, expand a result for npm metadata, install lifecycle scripts, recorded lock/registry digests, registry signatures and advertised provenance. Both PDF and JSON reports include these results and review steps, including the Remediation Plan.

Signals are explainable review prompts: one-edit/adjacent-transposition similarity against a disclosed fixed reference list, install lifecycle commands, and mismatched integrity strings for the strongest shared digest algorithm. Legitimate packages may trigger signals. Scoped names are excluded from name similarity. No popularity score, malware probability, or automatic replacement is inferred. Missing provenance is not a suspicious signal.

`CONFIRMED MALICIOUS` is reserved for a fresh OSV version match with a fetched, package-matching, non-withdrawn `MAL-` advisory; the source verdict is linked. Other heuristics and ordinary vulnerability advisories cannot produce that classification. This is an attributed malware verdict, not an independent code analysis, and advisory-detail coverage limits apply. `SUSPICIOUS`, `NO SIGNALS`, and `UNKNOWN` are distinct states; missing metadata may coexist with a locally detected suspicious name.

Metadata checks are limited to 100 unique exact npm package/version pairs, 1,000 included instances, a 15-second deadline, and 1 MiB per response. Duplicate instances share requests. Known custom registry tarball sources are skipped. Unknown, private, omitted, or unavailable metadata does not imply safety. Package names and exact versions are sent to public npm when no custom source is recorded; manifests without source identity cannot establish registry origin. Old scans need rescanning to capture lockfile integrity/resolved fields.

Integrity is a metadata digest comparison, **not** verification of tarball or installed bytes. Signatures and provenance are displayed as registry-advertised, **not cryptographically verified**. No tarballs, attestation URLs, publisher repository URLs, or lifecycle scripts are fetched or executed. Use `npm audit signatures` in a trusted environment to verify supported signatures and provenance; provenance alone is not a safety guarantee. See [npm provenance guidance](https://docs.npmjs.com/viewing-package-provenance/) and [npm registry metadata](https://github.com/npm/registry/blob/main/docs/responses/package-metadata.md).

### Before-and-after rescans

In a scan's Overview, open **Before-and-after rescan**. The active scan is the baseline. Make any code/dependency changes yourself, then **Scan updated repository / ZIP**, or choose another saved scan as the after state. Declare that both scans represent the same project and select **Compare vulnerabilities**. The workflow reads captured files as data; it never changes source files, manifests or lockfiles, installs packages, or executes submitted scripts.

Both inventories are checked together against current OSV data, deduplicating identical versions. Results group exact package/advisory IDs across installations and show all before/after versions and paths:

- **Resolved:** observed before, absent after with complete relevant checks and an inventory with roots and no warnings/unresolved declarations; includes dependency removal.
- **Remaining:** observed in both, even when affected duplicate instances decrease.
- **Newly introduced:** observed after, absent before with complete relevant baseline checks and no baseline inventory gaps.
- **Unverifiable:** the required absence cannot be established, a check is unknown/paginated, or inventory coverage has gaps. Coverage rows are included and are not distinct known vulnerabilities.

The comparison retains inventory hashes, scan/check timestamps, warnings, exact OSV checks and limitations. It compares saved inventories using current advisory knowledge, not historical advisory states. Advisory aliases are not merged; an advisory ID change can look resolved/new. User-declared project lineage is not independently verified. Outcomes do not establish causality, exploitability or compatibility. Suspicious-package signals remain a separate report section.

Comparison JSON is downloadable. On the **after scan**, generate/regenerate Security Findings and Remediation Plan to embed the saved comparison in both PDF and JSON reports. Comparisons are saved across restarts; repeating a comparison replaces the after scan's saved comparison. Existing security-report snapshots retain their earlier evidence until regenerated.

API: `POST /api/scans/:afterId/comparison` with `{ "beforeScanId": "...", "sameProject": true }`; `GET /api/scans/:afterId/comparison` downloads the saved result. Distinct IDs are required. Comparisons permit one active job and four requests per minute per client. Existing OSV query limits apply across the combined inventories.

Controlled repository fixtures in `tests/fixtures/rescan-before` and `tests/fixtures/rescan-after` cover fixed versions, removals, remaining duplicate instances, new vulnerabilities and a simulated lookup failure. Tests use deterministic OSV responses, compare fixture contents before/after, and exercise ZIP uploads, persistence, report embedding, outages, pagination and incomplete inventories without downloading or executing fixture packages.
